# 接口文档聚合保存与全量替换语义设计

## 1. 背景

阶段 2.1 至 2.6 已完成接口文档维护入口、文档状态、完整性校验、后台表单拆分、请求参数所有权和响应字段树规则。阶段 1 与阶段 2 的前置工作还提前实现了 2.7 的大部分基础能力：

- `GET /interfaceDoc/get` 已返回文档状态和聚合详情。
- `POST /interfaceDoc/save` 已统一保存文档主信息、全部参数、错误码和文档状态。
- 后端 DTO 与 Service 已拒绝缺失或为 `null` 的 `params`、`errorCodes`。
- 显式空数组已经表示确认清空，Service 事务已经执行参数和错误码全量替换。
- 文档保存和接口信息更新已经通过数据库当前状态及接口主记录行锁限制为仅 `OFFLINE` 可写。
- 前端已经提交参数与错误码全量快照，保存期间禁止重复提交，保存成功后重新查询聚合详情。

本轮不重复改造上述已完成逻辑，只补齐两个仍缺少明确保障的边界：

1. 前端当前把聚合响应中缺失的 `requestParams`、`responseParams`、`errorCodes` 静默转换为空数组，可能把不完整加载误解释为管理员确认清空。
2. 后端现有测试覆盖缺失集合、`null` 集合和显式空数组，但缺少“已有非空数据被第二次非空全量快照完整替换”的集中验收证据。

## 2. 目标与非目标

### 2.1 目标

- 聚合详情必须显式返回请求参数、响应参数和错误码三个集合，合法空集合使用 `[]` 表达。
- 前端只有在三个集合均存在且均为数组时才把响应转换为编辑模型。
- 聚合响应转换采用先计算、后提交方式，任一转换失败时不得把部分数据写入页面编辑状态。
- 不完整聚合响应按加载失败处理，页面禁止保存并允许管理员重新加载。
- 保存请求始终提交请求参数、响应参数和错误码的完整快照。
- 保存成功后重新读取后端聚合详情，并以后端返回的排序、记录 ID 和文档状态重建编辑模型及基线快照。
- 后端测试证明第二次全量保存会移除旧响应字段和旧错误码，只保留新快照数据，同时保留运行时模板要求的完整请求参数快照。

### 2.2 非目标

- 不新增独立参数或错误码批量保存接口。
- 不修改现有 Service 全量替换算法、事务边界或数据库表结构。
- 不引入文档修订号、乐观锁、编辑锁或多管理员协同编辑。
- 不调整发布状态机、发布超时恢复或发布探测能力。
- 不提前实现阶段 2.8 的数量、字符数、JSON 字节数及请求体大小补强。
- 不为所有 HTTP 响应引入通用运行时 Schema 框架。

## 3. 聚合协议约束

### 3.1 查询响应

`InterfaceDocDetailVO` 的以下字段是文档维护页的全量集合契约：

- `requestParams`
- `responseParams`
- `errorCodes`

三个字段必须存在。没有对应数据时，后端返回空数组，不能省略字段或返回 `null`。后端当前查询实现已经为三个字段赋非空列表，本轮通过前端必需类型和运行时边界校验显式固化该契约。

`requestHeaders` 是系统动态派生的展示数据，不属于管理员保存快照，因此不纳入本轮完整性门禁。

### 3.2 保存请求

保存请求继续使用现有 `InterfaceDocSaveRequest`：

- `params` 同时包含全部请求参数和响应参数。
- `errorCodes` 包含全部接口级错误码。
- 字段缺失或为 `null` 表示请求无效。
- 显式 `params: []` 或 `errorCodes: []` 才表示管理员确认清空对应集合。

请求参数名称、位置、类型和必填性继续受运行时参数模板约束；全量替换不赋予文档维护页修改请求参数所有权的能力。

## 4. 前端设计

### 4.1 类型约束

在 `InterfaceDocDetailVO` 中，将 `requestParams`、`responseParams`、`errorCodes` 从可选字段改为必需字段。该调整使调用方在编译期必须明确处理三个集合，避免新增调用代码再次依赖缺失字段兜底。

其他仅用于展示或允许后端局部降级的字段继续保持现有可选语义。

### 4.2 完整性校验

维护页收到聚合响应后，先检查三个全量集合是否均满足 `Array.isArray`。任一字段缺失、为 `null` 或不是数组时，抛出明确的加载错误，例如“接口文档聚合数据不完整，请重新加载”。

错误处理沿用现有加载失败流程：

- `detail` 保持为 `null`。
- `loadError` 展示错误信息。
- 保存按钮因 `loadError` 和无有效详情保持禁用。
- 管理员可以点击“重新加载”再次请求。

### 4.3 原子转换

加载过程按以下顺序执行：

1. 请求聚合详情。
2. 校验三个全量集合完整存在。
3. 在局部变量中构造文档主信息、请求参数、响应参数和错误码编辑模型。
4. 使用局部编辑模型构造本次后端快照对应的基线。
5. 只有上述步骤全部成功后，才一次性更新 `detail`、表单字段、参数集合、错误码集合和 `baseline`。

这样即使字段映射、父级关系转换或后续新增的模型校验抛出异常，页面也不会处于“主信息来自新响应、集合仍来自旧响应”的混合状态。

### 4.4 保存与回读

现有保存流程保持不变：

1. 从当前编辑模型构造文档主信息、全部请求参数、全部响应参数和全部错误码快照。
2. 保存期间设置 `saving`，禁用所有编辑和保存操作，并拒绝重复调用。
3. 保存成功后重新执行完整加载流程。
4. 使用后端回读的排序、记录 ID 和文档状态重建会话内 `paramKey`、页面内容和基线快照。
5. 回读失败按保存失败处理，不把提交前的编辑状态错误标记为已同步。

## 5. 后端验收设计

生产代码继续使用现有 `InterfaceDocServiceImpl.saveDoc` 事务：先完成全部校验，再保存文档主信息，随后全量替换参数和错误码。任一子项失败时由现有事务统一回滚。

新增集成测试使用同一接口连续保存两次：

1. 第一次保存运行时请求参数、旧响应字段和多条旧错误码。
2. 第二次提交完整请求参数、新响应字段和新的错误码快照。
3. 查询数据库与聚合详情，确认旧响应字段和旧错误码均不存在。
4. 确认新响应字段的父子关系、排序及新错误码准确返回。
5. 确认运行时请求参数仍完整存在，证明第二次请求提交的是全部参数快照而不是局部响应字段补丁。

已有缺失字段、`null` 字段、显式空数组和事务回滚测试继续保留，不重复建立等价用例。

## 6. 错误处理与安全边界

- 不完整聚合响应属于客户端无法安全编辑的数据契约错误，必须阻止保存，不能降级为空集合。
- 前端校验只负责防止误操作，后端 DTO 与 Service 双重非空校验继续作为权威保护。
- 后端仍在全量删除旧数据前完成参数所有权、响应字段树、文档完整性和内容安全校验。
- 本轮不改变鉴权、CSRF、敏感内容校验及管理员权限规则。
- 所有错误信息继续按纯文本展示，不引入 HTML 渲染。

## 7. 测试范围

### 7.1 后端

- 聚合保存用新的非空快照完整替换旧响应字段和旧错误码。
- 新快照查询结果不包含任何旧集合记录。
- 请求参数继续满足运行时模板所有权约束并完整保留。
- 运行既有 `InterfaceDocControllerTest`，确认缺失、`null`、空数组、状态门禁和事务语义无回归。

### 7.2 前端

- `requestParams` 缺失、为 `null` 或不是数组时禁止进入可保存状态。
- `responseParams` 缺失、为 `null` 或不是数组时禁止进入可保存状态。
- `errorCodes` 缺失、为 `null` 或不是数组时禁止进入可保存状态。
- 合法空数组可以成功加载并允许管理员按现有规则编辑。
- 保存载荷同时包含请求参数、响应参数和错误码全量快照。
- 保存成功后发生第二次查询，并使用回读的新排序、ID 和状态刷新编辑模型。
- 运行维护页定向测试、前端全量测试、ESLint、类型检查和生产构建。
